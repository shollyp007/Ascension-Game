Executive summary

Ascension is a single-player, story-driven game built in Unreal Engine 5. The player takes up one of three lives — a prophet, a high-school student, or a nurse — and climbs a mountain that rises over a village. Each stage of the climb is a trial set by the Village Master and worked against by tempting spirits. The trials are won not with weapons but with Scripture: the player who knows the word of God, and how to apply it, advances; the player who does not, falls. The tempters know the word too, and quote it out of shape — as in Matthew 4.

The project is scoped to a single, fully polished vertical slice: one character, the village and the first stretch of mountain, and one complete trial — the trial of the flesh — playable from start to resolution, with a character-select menu, a faith / resolve meter, win and lose states, a prison scene, and a working save file. The wider game is designed on paper and presented as concept. Unreal’s editor MCP (Model Context Protocol) is used to accelerate level blockout, set dressing, and Blueprint scaffolding.

The remainder of this document sets out the concept, the scope boundary, the technical approach, the core mechanic and its scriptural grounding, and a week-by-week development roadmap with deliverables, exit criteria, risks, and assessment mapping.

Vision & concept

The village sits in the shadow of a mountain. To leave it — to ascend — is to be tested. The Village Master sets the trials; the tempting spirits work against the player at every stage. The design intent is a game that teaches biblical literacy and discernment through play: the player learns not only what Scripture says but how it is rightly applied, by contrast with how it is twisted.

Player fantasy

“I stood in front of something that wanted me to fall, and I answered it with the truth, and it had no more power over me.”

Pillars

  • Scripture as strength. Progress is gated on knowledge and discernment, never reflex or force.
  • The tempter is literate. Encounters are a contest of interpretation, modelled on Matthew 4 — “It is written… It is also written.”
  • Failure teaches. A wrong answer always ends with the correct passage and its explanation, so a loss is still a lesson.
  • Restraint. Temptation is dialogue and choice, never depiction.

Scope: what the capstone delivers

The full concept — three playable characters, a realistic village, an ascending series of levels, a dialogue system, spirit AI, a Scripture-knowledge mechanic, save and progression, and win / lose states with a prison — is two to three years of work for a team. The capstone delivers one vertical slice, built and polished end to end, with the rest designed on paper. This boundary is treated as frozen; changes go to a backlog rather than into the build.

Built for the capstone

  • One character — the high-school student (simplest to model, rig, and dress)
  • One environment — the village and the first stretch of mountain
  • One trial, fully playable — the trial of the flesh (seduction)
  • Character-select menu with persistence across levels
  • Faith / resolve meter and tempter influence meter with UI
  • Pass and fail resolution; the prison scene; a working save file

Designed on paper, shown as concept

  • The money and the wealth / status trials
  • The prophet and the nurse
  • Levels beyond the first
  • The Village Master as a character
  • Any form of multiplayer

A capstone rewards one thing that works and is documented far above five things that are broken. The slice is framed as “Act I” of a larger vision.

The Unreal MCP workflow

The Unreal MCP servers let a language model drive the editor through Python and Remote Control. The division of labour is deliberate.

Used for

  • Greyboxing and layout — a village street grid, fences, props, in bulk
  • Populating the scene with NPCs and set dressing
  • Scaffolding Blueprints and UMG widgets, wiring simple logic
  • Repetitive edits — retag every spirit, batch-set materials
  • Procedural placement through editor Python

Not relied on for

  • Realism — from Fab / Megascans assets, Nanite, Lumen, PCG foliage, and lighting
  • Art direction and mood
  • Gameplay feel and balance

Pipeline: acquire a complete village kit → assemble and populate it with MCP → scaffold the gameplay Blueprints with MCP → art-direct the lighting and composition by hand. Every MCP action has a manual fallback, so the tool is an accelerator, not a dependency.

Technical architecture

  • Engine: Unreal Engine 5.4+, built on the Third Person template.
  • Logic: Blueprints for nearly everything; C++ only where unavoidable.

Core systems

  • Character selection — a menu level writes a SelectedCharacter value into a GameInstance so it survives level loads.
  • Trial / encounter — a BP_Trial actor with a trigger volume freezes movement and starts a dialogue encounter on overlap.
  • Dialogue & choice UI — a plugin (DlgSystem, Not-Yet-Dialogue, or Dialogue Tree), not hand-rolled.
  • Scripture knowledge check — the core mechanic (Section VI), driven by a Data Table.
  • Resolution — a pass raises the faith stat and opens the path up; a fail teleports to the prison level and shows a game-over screen with the relevant verse and an invitation to try again.
  • Save — an Unreal SaveGame object holding character, current level, faith stat, and trials passed; the struct is versioned from the start.
  • Spirits — dialogue actors that patrol a spline or run a simple Behavior Tree; the attack is verbal — they approach and open a trial.

Core mechanic — Scripture encounters

The design anchor is the temptation of Christ (Matthew 4 / Luke 4). Satan quotes Scripture — “It is written” — and Jesus answers with better-fitted Scripture — “It is also written.” That is the combat system.

  1. The tempter makes a proposition and backs it with a real but misapplied verse.
  2. The player is given three or four responses. One is a correctly applied Scripture; the others are plausible worldly reasoning or misused verses.
  3. A right answer drops the tempter’s influence meter. A wrong answer drops the player’s resolve meter.
  4. Three to five exchanges per encounter. Resolve runs out → the player falls → prison. The tempter’s influence breaks → the player ascends.

Content pipeline

Each row of a Data Table is one exchange: the tempter’s line, the misused reference, four options each flagged bIsCorrect, and an explanation shown afterward whatever the outcome — so the player learns. Content is authored in a spreadsheet, kept separate from code, and handed to a qualified reviewer.

The Scripture content is reviewed by someone qualified in the relevant tradition before it ships. A game meant to teach the Bible cannot afford to misquote or misapply it.

The three first-layer trials

The trials are framed as the triad of 1 John 2:16, giving the level ladder a scriptural spine that is cited throughout the written report. The capstone builds the first; the other two are designed only.

Lust of the flesh

Seduction — built

Tempting spirits press the player toward fornication through flattery and proposition. Verbal and symbolic only, never depicted.

Proverbs 7 · 1 Cor 6:18 · 2 Tim 2:22

Lust of the eyes

Money — designed

Gain by compromise — a bribe, a theft framed as need, a lie that pays. The offer looks like provision.

1 Tim 6:9–10 · Prov 30:8–9 · Matt 6:24

Pride of life

Wealth & status — designed

Recognition, power, a name. “All this I will give you” — the summit offered without the climb.

Matt 4:8–10 · Jer 9:23–24 · James 4:6

Handling the seduction theme

  • Verbal and symbolic, never depicted. The temptation is the dialogue and the choice, not any imagery. The tempter flatters and propositions in text; the player answers.
  • On failure: fade to black, then the prison scene with a verse framed as instruction, not punishment.
  • No nudity, no sexual content, no suggestive animation. This holds a teen-appropriate rating, stays defensible in an academic setting, and makes a better teaching tool.

Development roadmap

Roughly 14 weeks, solo. Each phase names its tasks, its deliverables, and an exit criterion that must be met before the next phase begins. If the schedule slips, the non-negotiable core is: the menu, one trial, pass / fail, the prison, and the written report.

PHASE 0

Pre-production

Weeks 1–2

Tasks

  • Finalise this document with the supervisor and freeze scope
  • Install and validate one Unreal MCP server; run a smoke test (spawn and move actors by prompt)
  • Create the UE5 project from the Third Person template; commit the skeleton; set up Git LFS
  • Select the dialogue plugin; source and evaluate a village environment kit; decide the art target (stylised vs full realism)
  • Line up the doctrinal reviewer

Deliverables

  • Approved design document · running UE5 project in the repo · MCP smoke-test recording · asset shortlist
Exit criterionMCP can place and modify actors on command, and the project opens clean on a fresh clone.
PHASE 1

Environment

Weeks 3–4

Tasks

  • Import the village kit; MCP-assisted blockout of the village and the first mountain path
  • Navigation mesh; collision; checkpoint volumes
  • First Lumen lighting pass (single day setting); skybox; atmosphere
  • Player character traversal and camera tuning

Deliverables

  • A walkable village and mountain stretch · first-look screenshots and a fly-through video
Exit criterionThe player can walk from the village square to the trial location and up to the “level 2” gate without falling through geometry.
PHASE 2

Core systems

Weeks 5–8

Tasks

  • Character-select menu → GameInstance persistence
  • BP_Trial trigger → encounter flow; integrate the dialogue plugin
  • Design the Scripture Data Table schema; wire a placeholder trial from it
  • Resolve and influence meters + UMG HUD; pass / fail resolution
  • Prison level and game-over / continue flow
  • Versioned SaveGame (character, level, faith, trials passed); main menu with Continue

Deliverables

  • One placeholder trial playable start to finish, with working save and load
Exit criterionA tester can start a new game, fail a trial to the prison, reload, pass it, and reach the mountain path — with no code changes between runs.
PHASE 3

Content — the seduction trial

Weeks 9–10

Tasks

  • Write the five-exchange seduction script — misapplied vs correctly applied Scripture for each
  • Doctrinal review and sign-off; revise
  • Author the reviewed content into the Data Table; write the explanation screens
  • Build the tempter spirit — patrol spline, approach behaviour, trial trigger
  • Dialogue presentation styling; optional voice-over

Deliverables

  • The trial of the flesh — complete, reviewed, and in the build
Exit criterionReviewer sign-off received, and the trial passes a playtest for clarity and difficulty.
PHASE 4

Polish & playtest

Weeks 11–12

Tasks

  • Audio — ambience, music, UI and outcome stingers
  • Meter tuning from playtest data; difficulty balance
  • UI polish; bug triage; performance pass (Nanite / Lumen scalability)
  • Accessibility — text size, subtitles, remappable input, reduced-motion option

Deliverables

  • A release-candidate slice build · a written playtest report
Exit criterionNo known blocker or crash bugs; the average tester completes the slice unaided.
PHASE 5

Submission

Weeks 13–14

Tasks

  • Written report; narrated demo video (5–8 minutes); presentation deck
  • Packaged Windows build; v1.0-slice git tag and GitHub release
  • Final repository tidy; README and documentation updated

Deliverables

  • Report · demo video · presentation deck · packaged build · tagged release
Exit criterionAll artifacts committed to the repository, and a dry-run presentation completed.

Success criteria & assessment mapping

The slice is considered successful when a first-time player can select a character, attempt the seduction trial, lose to the prison, reload, and win through to the mountain path — understanding, at the end, which Scripture applied and why.
